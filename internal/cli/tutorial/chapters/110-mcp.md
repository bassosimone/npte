# An MCP server for autonomous agents

The previous chapters drive `npte` from a human shell prompt. This
one wires the same primitives into an autonomous coding agent
(Claude Code, Cursor, …) over the [Model Context Protocol][mcp], so
the agent can build, shape, and tear down lab topologies on its
own.

`npte mcp serve` is a stdio MCP server. Most agents read a
project-scoped `.mcp.json` from the working directory when they
start; pointing that file at `npte mcp serve` is the entire
integration.

[mcp]: https://modelcontextprotocol.io/

## 1. The trust bridge

Coding agents typically run inside a confinement layer that blocks
`sudo`. That is the right default — but it also locks the agent
out of every primitive in this tutorial, because every primitive
needs `CAP_NET_ADMIN`.

`npte mcp serve` runs *outside* the agent's sandbox, listens for
MCP tool calls on stdio, and shells to `sudo npte …` on the
agent's behalf. The privileged side is kept safe by the same two
bounds that protect human users at a shell:

- the namespace registry fences every `netns`/`netem` verb to
  namespaces `npte` itself created (see the sudoers chapter); and
- `npte netns run` always runs the inner command under bubblewrap
  (see the sandbox chapter). The MCP enforces `--sandbox`
  unconditionally — the agent cannot disable it.

So the bridge is narrow: an agent that gains MCP access cannot
escalate beyond what `sudo npte` already allowlists for the
invoking user, and the user-supplied code path that `netns run`
exposes is always sandboxed.

## 2. Wiring it up

Drop a `.mcp.json` at the project root:

    {
      "mcpServers": {
        "npte": {
          "command": "/usr/sbin/npte",
          "args": ["mcp", "serve"]
        }
      }
    }

Use `/usr/local/sbin/npte` instead if you installed from source.
The absolute path must match the path the sudoers snippet binds to
— otherwise the agent's first privileged tool call will hit a
password prompt and hang the bridge.

When the agent starts in this directory, it spawns `npte mcp
serve` as a child process and talks JSON-RPC over its
stdin/stdout. The server inherits the agent's working directory
and writes its session artifacts there, so every project gets its
own server with its own state. There is no daemon, no socket, no
shared state across projects.

Most clients ask you to approve the MCP server on first connect
and persist the decision per project; subsequent sessions in the
same directory reconnect silently. If you edit `.mcp.json` after
the agent has already started, a *full restart* of the agent
session is usually required — most clients read the file at
session start, not on reconnect.

## 3. What the agent gets

`npte mcp serve` exposes a small fixed toolbox:

- `lab_create`, `lab_destroy` — the canned three-node lab from
  chapter `routing`.
- `netns_list`, `netns_show` — read-only introspection of
  npte-managed namespaces.
- `shape_download`, `shape_upload` — condition the client's
  download or upload path at the router. Each tool clears any
  existing qdisc before applying, so it is always safe to call.
- `shape_clear` — remove shaping from both paths.
- `run_command` — run a command inside a namespace synchronously
  (blocks until done, returns exit code inline). Set `count` > 1 to
  repeat the command; each run is captured separately. Always sandboxed.
- `start_command` — start a long-lived command inside a namespace
  as a background process. Always sandboxed.
- `wait`, `kill` — observe and signal `start_command` processes.

Most tools run synchronously: the call blocks until `npte` finishes
and the exit code is returned inline. `run_command` follows this
pattern with a caller-specified timeout — use it for commands whose
result you need before proceeding (an iperf3 client, curl, ping).
Set `count` > 1 to repeat the same command sequentially; each run
gets its own procId and session directory, and results come back as
an ordered list of steps — no bash loops needed.
The shape tools may run multiple npte invocations internally (clear +
apply) and return the result of each step.

`start_command` is the exception: it forks `sudo npte …` in the
background and returns a `procId` immediately; the agent then polls
`wait <procId>` to learn the exit code. This decoupling is what
makes long-running commands (an iperf3 server, a persistent listener)
tractable over MCP's request/response shape.

`gateway` and `container` are deliberately not exposed, for the
same reason they are not in the sudoers allowlist: their
privileged surface is broader than the registry bound can fence.
If you need real internet egress in an agent-driven workflow, run
`gateway` yourself at a shell and let the agent layer `lab` work
on top.

The shared trust-bridge framing, session layout, sandbox-escape
rule, and lifecycle contract are shipped to the agent once at
handshake via MCP's `instructions` field, so the agent learns them
without each per-tool description having to repeat them.

## 4. The session directory

Each `npte mcp serve` invocation mints a UUIDv7 *session ID* at
startup and roots its on-disk state at
`./.npte/sessions/<sessionId>/`. Every tool call writes four files
into a per-process subdirectory under that root:

- `argv.json` — the exact `sudo npte …` command that was forked.
- `stdout.txt`, `stderr.txt` — captured streams of the inner
  command.
- `exitcode.txt` — written *after* termination (its absence is a
  signal that the process is still running).

The MCP server only ever writes these files; it never reads them
back. The agent reads them out of band (typically via its own
`Bash` or `Read` tool), which keeps the protocol surface tiny and
lets the agent paginate, grep, or post-process the output however
it wants. The per-process directory survives a `wait` reap, so it
remains available for inspection after the agent has moved on.

Restarting the agent (or the MCP server) mints a fresh session ID,
so `./.npte/sessions/` accumulates one subdirectory per
invocation — chronologically sortable, easy to `mv` into an
archive directory when an activity is done, easy to `rm -rf` when
it is not worth keeping. Add `.npte/` to `.gitignore` if you do
not want session artifacts checked into the repository.

## 5. Caveats

- **The sandbox's writable path is the agent's working directory.**
  `npte mcp serve` inherits the agent's CWD, and the bubblewrap
  sandbox that wraps every `run_command`/`start_command` rebinds
  that directory read-write (see the sandbox chapter). Launched
  from a project directory, that is exactly the blast radius you
  want. Launched from `$HOME`, it means agent-authored code running
  inside the sandbox can write to your dotfiles — persistence as
  your user that survives every other confinement layer. Start the
  agent from a dedicated project directory, never from `$HOME`.

- **`kill` only sends `SIGINT`.** `SIGKILL` cannot be relayed
  through `sudo` and is intentionally not exposed. Prefer
  signal-friendly inner commands.

- **The signal-propagation chain is lossy.** `sudo → npte → ip
  netns exec → runuser → bwrap` traverses several supervisors,
  and bwrap's `--die-with-parent` arms `PR_SET_PDEATHSIG=SIGKILL`
  on the inner process. Inner commands frequently exit with
  `signal: killed` after a `kill`, not with a clean SIGINT-driven
  exit. Treat a nonzero exit after `kill` as expected, not as
  failure.

- **One-shot reap.** Once `wait` returns `terminated=true`, the
  `procId` is removed from the server's in-memory table.
  Subsequent `wait` or `kill` on the same `procId` return "no
  such process". The on-disk per-process directory survives —
  read it, do not re-poll.

## Recap

- `npte mcp serve` is a stdio MCP server that exposes the
  `netns`/`netem`/`lab` primitives to an autonomous agent that
  cannot shell to `sudo`.

- Wire it into a project with a `.mcp.json` pointing at the npte
  binary; the agent spawns one server per project. No daemon.

- The trust bridge inherits the sudoers registry and `--sandbox`
  bounds — the agent cannot escalate beyond what they already
  allow for human users.

- Most tools — including `run_command` — run synchronously; shape
  tools may run multiple steps internally. `start_command` is
  asynchronous (`wait` observes termination). Every artifact is
  captured under `./.npte/sessions/<sessionId>/<procId>/`.

- `kill` is SIGINT-only; the cleanup chain is signal-lossy; reap
  is one-shot. Read the per-process directory, not the protocol,
  for the data you care about.
